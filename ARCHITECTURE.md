# Архитектура Farma

## 1. Архитектурная идея

Farma — каталог сущностей с генерируемым представлением, а не набор вручную написанных HTML-страниц. Источник истины — структурированные данные; страница — способ представить их человеку и поисковому роботу.

## 2. Логические слои

### Данные
Записи о препаратах, действующих веществах, торговых наименованиях, производителях, формах, дозировках, упаковках, регистрационных сведениях и источниках.

На первом этапе допустимы JSON/YAML-файлы в репозитории. При росте объёма способ хранения можно заменить без изменения предметной модели.

### Валидация
Перед сборкой проверяем обязательные идентификаторы, корректность ссылок, допустимые значения справочников, дубли, наличие источников у значимых утверждений, корректность slug и отсутствие конфликтующих URL.

Невалидная запись не должна незаметно попадать в публикацию.

### Представление
Шаблоны строят страницы конкретного варианта препарата, действующего вещества, производителя (когда данных достаточно), справочников и поиска.

Не создавать индексируемые страницы для пустых или почти дублирующих сущностей.

### Поиск и навигация
В MVP — простой поиск по названию и действующему веществу, если объём каталога это оправдывает. Поиск не подменяет медицинский подбор.

### Публикация
GitHub хранит исходники и данные. Netlify собирает статический сайт при изменениях в основной ветке и публикует результат.

## 3. Поток публикации

1. Добавляется или обновляется запись.
2. Указываются источники и даты проверки.
3. Проверка данных выявляет ошибки и конфликты.
4. Генератор строит страницы, метаданные и sitemap.
5. Netlify публикует сборку.
6. После публикации проверяются URL, canonical, robots и доступность страниц.

## 4. URL и идентичность

Внутренний ID сущности не зависит от названия или URL. Slug предназначен для удобочитаемого адреса и может меняться отдельно от идентификатора.

Предварительная логика:
- вариант препарата: /drug/{slug}/;
- действующее вещество: /ingredient/{slug}/;
- производитель: /manufacturer/{slug}/.

URL-структура будет утверждена после проверки примеров и языковой стратегии. При смене slug нужен 301 redirect со старого адреса.

## 5. Языки

Языковая стратегия пока не зафиксирована. До её утверждения не следует автоматически размножать страницы на несколько языков.

Если будут поддерживаться украинский и русский, языковые версии должны иметь отдельные URL, корректные hreflang и canonical. Перевод не меняет идентичность сущности; медицинские термины сверяются, а не переводятся механически.

## 6. Что не строим сейчас

Не вводим микросервисы, отдельную базу данных и API без необходимости, кабинеты, сложную рекомендательную систему, аптечные интеграции, динамические цены и остатки.

## 7. Когда пересматривать архитектуру

Переход к базе данных или отдельному API оправдан при измеримых ограничениях файлового подхода: частые параллельные обновления, сложные связи, большой объём, редакторский workflow или интеграции с внешними источниками.
